# 本地编译教程 & GitHub 工作流编译教程

本仓库有两条编译路径，**共用同一套流程脚本** `Scripts/build-core.sh`，所以在同一份源码、同一个分支下，两边跑出来的配置和固件行为是一致的——本地能编过的配置，云上也能编过。

| 路径 | 适用场景 | 入口 |
| ---- | -------- | ---- |
| **GitHub 工作流（云编译）** | 日常自动出固件、手动出正式版，不占用自己的机器 | `.github/workflows/*.yml` |
| **本地 Ubuntu 编译** | 调试试错、临时改配置、验证新驱动/新插件、不想消耗 Actions 额度 | `Scripts/local-build.sh` |

> 第一次接触这个仓库，建议先看 [README.md](../README.md) 了解固件机型与目录结构，再按本文档操作。

## 第 0 章 通用知识

### 0.1 目录与文件职责

| 路径 | 作用 |
| ---- | ---- |
| `.github/workflows/WRT-CORE.yml` | 云编译核心流程，被其它工作流调用，内部只调用 `Scripts/build-core.sh` |
| `.github/workflows/WRT-TEST.yml` | 通用云编译入口（可选平台/源码/分支，默认只输出配置） |
| `.github/workflows/AIR-TCBOOT.yml` | 贝尔系列 tcboot 固件定时编译（每月 1 日 UTC 3:00 / 北京 11:00），上游无更新自动跳过 |
| `.github/workflows/Auto-Clean.yml` | 清理旧 Release / Tag 与旧 Workflow 记录（两条设备线各保留最新 2 个）；**定时触发已关闭，只能手动运行** |
| `.github/workflows/AIR-ONU.yml` | ONU（uboot）固件编译，由 AIR-TCBOOT 完成后自动触发，也可手动触发 |
| `.github/workflows/Cache-Clean.yml` | 清理 Actions 编译缓存；**定时触发已关闭，只能手动运行** |
| `Scripts/build-core.sh` | 流程主体：feeds → 插件 → 配置 → 下载 → 编译（云/本地共用） |
| `Scripts/local-build.sh` | 本地编译入口：环境检查、拉源码、调用 build-core |
| `Scripts/Packages.sh` | 自定义插件仓库克隆与版本更新 |
| `Scripts/Settings.sh` | 固件默认参数（主题/主机名/IP/WiFi/密码）注入 |
| `Scripts/Handles.sh` | 插件相关的收尾处理（由 `build-core.sh` 调用） |
| `Config/<平台>.txt` | 各平台 `.config` 片段（含 `CONFIG_TARGET_*`） |
| `Config/GENERAL.txt` | 全平台通用片段，非 TEST 配置都会自动拼接在平台片段之后 |
| `Config/PRIVATE.txt` | 私有配置片段（可选），最后追加到 `.config`，可加进 `.gitignore` 不公开 |
| `Scripts/PRIVATE.sh` | 私有扩展脚本（可选），在插件克隆完成后执行 |

### 0.2 配置文件拼接顺序

本地与云端**完全一致**，顺序如下（后面的会覆盖前面的同名项）：

```
Config/<平台>.txt   →   Config/GENERAL.txt   →   Config/PRIVATE.txt   →   命令行/参数追加（PACKAGE / -p）
```

> `TEST` 配置是个例外：它不拼接 `GENERAL.txt`，只读自己一份。
> ONU / TCBOOT / MAIN 三份平台配置都建立在 `GENERAL.txt` 之上，所以**通用插件和驱动尽量只写在 `GENERAL.txt`**，避免多份配置重复维护、互相打架。

## 第 1 章 本地编译教程（Ubuntu）

### 1.1 环境要求

| 项目 | 建议 |
| ---- | ---- |
| 系统 | Ubuntu 22.04 / 24.04（其它 Debian 系需自行装依赖） |
| 磁盘 | **完整编译预留 ≥ 40 GB**（源码+工具链+产物，实测一路编下来 11 GB 起，编完更大）；只生成配置（`--test`）≥ 6 GB |
| 内存 | ≥ 8 GB；并行数默认按「CPU 核数」与「内存 × 2/3」取小值自动算（8 GB 内存约 4 路，4 GB 约 2 路），也可用 `-j N` 手动指定 |
| 网络 | 需要能访问 GitHub（国内建议用 `--proxy`） |

### 1.2 安装编译依赖

```bash
sudo apt update
sudo apt install -y build-essential clang flex bison g++ gawk gcc-multilib g++-multilib \
  gettext git libncurses-dev libssl-dev python3-setuptools python3-dev rsync swig \
  unzip zlib1g-dev file wget curl libelf-dev jq
```

脚本会自动检测依赖，缺失时给出安装命令；也可以直接加 `--install-deps` 让它自动装（需要 sudo）。

> 若报 `libncursesw5-dev` / `libncurses-dev` 相关缺失，按提示补装即可（不同 Ubuntu 版本包名略有差异）。

### 1.3 准备仓库

```bash
git clone <你的仓库地址> OpenWRT-CI-XG-040G-MD
cd OpenWRT-CI-XG-040G-MD
```

脚本必须在**仓库根目录内**执行，它靠自身位置推导 `WRT_WORKSPACE`。

### 1.4 第一步：只验证配置（推荐）

先跑 `--test`：拉源码、装插件、生成 `.config`，但**不编译固件**，用来快速确认配置本身没问题。

```bash
bash Scripts/local-build.sh --test
```

- 耗时：约 5～15 分钟（取决于网速）
- 成功标志：终端出现各阶段完成提示，且 `<源码目录>/.config` 已生成
- 想跳过依赖检查再快一点：`--skip-deps`

配置生成后想微调插件：

```bash
bash Scripts/local-build.sh --test --menuconfig
```

### 1.5 第二步：完整编译

```bash
# 前台跑（能实时看日志，中断即停）
bash Scripts/local-build.sh

# 更推荐：后台跑并留日志，SSH 断开也不怕
nohup bash Scripts/local-build.sh > build.log 2>&1 &
tail -f build.log
```

- 耗时（8 核 / 8 GB 虚拟机、显式 `-j 8` 实测；现在默认会按内存自动降到 4 路，首次全量耗时会相应拉长，想复现这组数字就加 `-j 8`）：
  - **首次全量**（源码目录为空）：约 3～4 小时。其中 `rust` host 包一项就占 1.5～2 小时（它内部还要构建一套 LLVM）
  - **之后的日常编译**（默认行为）：**5～15 分钟**，只重编你改动过的部分。第一次花出去的几个小时，就是为这里铺路的
  - **加 `--clean` 的干净重编**：2～3 小时。`make clean` 会连 `staging_dir/hostpkg/stamp/` 一起清掉，`rust` 每次都要从头重编
- 编译中查看是否正常：`pgrep -c -f 'make|gcc|cc1'` 有进程在跑就是正常
- 想指定平台与并行数：

```bash
bash Scripts/local-build.sh -c AIROHA-ONU           # 默认就是它
bash Scripts/local-build.sh -c AIROHA-TCBOOT
bash Scripts/local-build.sh -c X86 -j 4
```

### 1.6 产物位置

| 内容 | 路径 |
| ---- | ---- |
| 生成的配置 | `<源码目录>/.config` |
| 固件 | `<源码目录>/bin/targets/<平台>/<机型>/`（如 `bin/targets/airoha/an7581/`） |
| 校验文件 | 同目录下的 `sha256sums` |
| 编译日志 | 建议 `cmd 2>&1 \| tee build.log` 或 `nohup … > build.log 2>&1 &` |

### 1.7 全部参数

| 参数 | 说明 |
| ---- | ---- |
| `-c, --config NAME` | 配置名，对应 `Config/NAME.txt`，默认 `AIROHA-ONU` |
| `-d, --dir DIR` | 源码目录，默认 `~/openwrt-build/<小写配置名>` |
| `-r, --repo REPO` | 上游源码，默认 `pbs05/ponwrt` |
| `-b, --branch NAME` | 上游分支，默认 `master` |
| `-j, --jobs N` | 并行任务数，默认按 CPU 与内存自动计算，可手动指定 |
| `-p, --package TEXT` | 追加 `.config` 内容，等价云编译的 `PACKAGE` 参数 |
| `-t, --test` | 只生成配置，不编译固件（仍会更新 feeds、克隆插件，需要网络） |
| `-m, --menuconfig` | 生成配置后进入 `make menuconfig` 手动微调 |
| `--install-deps` | 自动安装缺失依赖（需要 sudo） |
| `--skip-deps` | 跳过依赖检查 |
| `--force-clone` | 删除已有源码目录重新拉取 |
| `--update` | 复用源码目录时先拉到该分支最新提交（默认直接复用不更新） |
| `--clean` | 执行 `make clean` 彻底重编（默认跳过，走增量）。注意会清掉 rust 标记，多花 1.5～2 小时，发版前才需要 |
| `--proxy URL` | GitHub 加速前缀（国内必备），如 `--proxy https://ghfast.top/`；只在本次运行内生效，**不改动 git 全局配置** |

### 1.8 环境变量（覆盖固件参数与构建开关）

| 环境变量 | 默认值 | 说明 |
| ---- | ------ | ---- |
| `WRT_THEME` | `argon` | LuCI 主题（云编译 `WRT-TEST` 默认 `aurora`） |
| `WRT_NAME` / `WRT_SSID` / `WRT_WORD` / `WRT_PW` | `OWRT` / `OWRT` / `12345678` / 无 | 主机名、WiFi 名、WiFi 密码、登录密码 |
| `WRT_IP` | `192.168.100.1` | 管理地址 |
| `WRT_SKIP_CLEAN` | `true` | **默认 true，跳过 `make clean` 走增量编译**（5～15 分钟）。这是默认行为，因为它避免了 `make clean` 连带清掉 `staging_dir/hostpkg/stamp/` 里的 rust 标记（否则 rust 每次重编 1.5～2 小时）。发版前要绝对干净时设为 `false` 或用 `--clean` |
| `WRT_JOBS` | 按 CPU / 内存自动计算 | 并行任务数 |
| `WRT_WORKSPACE` / `WRT_DIR` | 脚本所在仓库 / `<workspace>/wrt` | 仓库根目录与源码目录 |

示例：

```bash
WRT_THEME=aurora WRT_SSID=MyWiFi WRT_WORD=12345678 WRT_IP=192.168.10.1 \
  WRT_SKIP_CLEAN=true bash Scripts/local-build.sh -c AIROHA-ONU
```

### 1.9 分步排障（直接调核心脚本）

某个阶段出问题时，可以只跑那一段：

```bash
bash Scripts/build-core.sh feeds      # 只更新 feeds
bash Scripts/build-core.sh packages   # 只克隆/更新插件
bash Scripts/build-core.sh config     # 只重新生成 .config
bash Scripts/build-core.sh download   # 只下载源码包
bash Scripts/build-core.sh compile    # 只编译固件
```

### 1.10 与云编译的差异

- **保留国内下载源**：云编译会删掉 `scripts/projectsmirrors.json` 里的国内源（GitHub 机器在国外），本地编译**不删**，下载更快。
- **没有 Actions 缓存**：cloud 有 ccache/toolchain 缓存，本地首次全量编译更慢属正常。
- **源码复用**：本地默认复用已存在的源码目录；要在复用前拉到该分支的最新提交用 `--update`，要换版本用 `--force-clone`。
- **产物复用**：默认跳过 `make clean`，`build_dir` / `staging_dir` / `dl` 全部保留，所以第二次起只需几分钟。
- **流程一致性**：feeds、插件、配置三个阶段与云编译共用同一份脚本。

### 1.11 常见问题

| 现象 | 处理 |
| ---- | ---- |
| 磁盘空间不足 | 清理空间，或用 `-d` 指向大分区 |
| 编译中途被 OOM kill | 降低并行 `-j 2`，或加 swap |
| `git clone` 极慢 / 超时（`gnutls_handshake() failed`） | 加 `--proxy https://ghfast.top/`（备用：`https://gh-proxy.com/`、`https://gh.llkk.cc/`） |
| `feeds update` 卡住 | 重跑一次即可（feeds 支持断点续传） |
| 上游源码拉不下来 | `-r` / `-b` 换源，或先手动克隆好再用 `-d` 指过去 |
| 想改完个别插件再编 | `-m` 进 menuconfig，或改 `Config/*.txt` 后重跑 |
| 编译失败想复现细节 | `cd <源码目录> && make -j1 V=s` 单线程重跑看报错 |
| 二次编译很慢（2～3 小时） | 检查是不是加了 `--clean`：`make clean` 会删掉 rust 的 stamp，导致它每次重编 1.5～2 小时。日常改动去掉 `--clean` 即可，5～15 分钟 |

### 1.12 实战经验（实测记录）

- 在 8 核 / 8 GB 的 Ubuntu 虚拟机上，从零到 `bin/targets/airoha/an7581/` 产出，全程稳定；编译期间 `make/gcc/cc1` 进程约 20～35 个属正常。
- 磁盘一定要给足：**建议 100 GB**，只跑 `--test` 也要 10 GB 上下。
- 用 SSH 登录服务器编译时，务必用 `nohup` 或 `tmux`，否则断线即中断。
- 定时观察进度的三件套：

```bash
tail -3 build.log                  # 当前阶段
pgrep -c -f 'make|gcc|cc1'         # 还有几个编译进程
df -h <源码目录所在分区>            # 磁盘余量
```

## 第 2 章 GitHub 工作流编译教程

### 2.1 自动流程（什么都不用做）

```
每月 1 日 11:00（北京时间，UTC 3:00）
  AIR-TCBOOT  → 检查上游 bingoguo93/immortalwrt@6.18 是否有新提交
               ├─ 无更新：跳过编译（省 Actions 额度），直接结束
               └─ 有更新：编译 AIROHA-TCBOOT → 记录上游 SHA
  AIR-ONU     → 自动编译 AIROHA-ONU（uboot 版）
```

固件与配置文件都会发布到仓库的 **Releases** 页面。

> 注意：`AIR-ONU` 的自动触发直接挂在 `AIR-TCBOOT` 的完成事件上，所以**只要 TCBOOT 跑完（哪怕上游无更新、跳过了编译）就会带起一次 ONU 编译**；手动跑 `AIR-TCBOOT`（含 `TEST` 模式）同样会带起 ONU。
>
> `Auto-Clean`（旧 Release / Tag / 旧 Workflow 记录）与 `Cache-Clean`（Actions 缓存）的**定时触发已关闭**，需要时手动运行——也就是说旧 Release 不会再被自动清理。

### 2.2 手动触发

1. 打开仓库 → **Actions**
2. 左侧选择工作流：
   - 出正式固件：`AIR-TCBOOT` 或 `AIR-ONU`
   - 临时试配置 / 编其它平台：`WRT-TEST`
3. 右侧 **Run workflow**，填参数后运行

### 2.3 AIR-ONU / AIR-TCBOOT 参数

| 参数 | 说明 |
| ---- | ---- |
| `PACKAGE` | 临时追加到 `.config` 的插件配置，多条用换行分隔，例如 `CONFIG_PACKAGE_luci-app-mosdns=y` |
| `TEST` | 勾选后**只输出配置文件**，不编译固件，用于快速验证配置是否会报错 |

> 主题 / 主机名 / WiFi / IP 等默认值写在对应 yml 的 `with:` 段（`WRT_THEME`、`WRT_NAME`、`WRT_SSID`、`WRT_WORD`、`WRT_IP`），改完提交即可。

### 2.4 WRT-TEST 参数

| 参数 | 说明 |
| ---- | ---- |
| `CONFIG` | 配置名（对应 `Config/<名字>.txt`），可选 `AIROHA-ONU` / `AIROHA-TCBOOT` / `AIROHA-MAIN` / `X86` 等 |
| `SOURCE` / `BRANCH` | 上游源码与分支 |
| `PACKAGE` | 追加插件配置 |
| `TEST` | 默认 `true`（只出配置），取消勾选才会真正编译 |

### 2.5 Release 命名规则

发布 tag 由「配置名 - 分支 - 日期」构成，例如 `AIROHA-ONU-master-2025.10.28`。同一 tag 已存在时不会再覆盖，需要重出就改配置或用 `WRT-TEST` 指定别的日期。

本仓库**只发 Release，不产生 Actions Artifact**（配置文件和固件都在 Release 里）。

### 2.6 云编译常见问题

| 现象 | 处理 |
| ---- | ---- |
| 没出固件 | 先看 Release 有没有新 tag；`AIR-TCBOOT` 在上游无更新时会主动跳过，属正常 |
| 想知道配置能不能过 | 手动跑一次并勾选 `TEST`，几十分钟内就能在 Release 里拿到 `Config-*.txt` |
| 编译环境异常 / 缓存坏了 | 手动运行一次 `Cache-Clean` 再重跑 |
| 某次 run 失败 | Actions 页面进入失败 run → **Re-run failed jobs**，无需改代码 |
| 失败卡在 `Download Packages`，注解里是 `No space left on device` | 托管 runner 磁盘规格不统一（有的没有独立 `/mnt`，根分区只有十几 G）；工作流已改为按可用空间自适应建 swap 并提前释放根分区，若仍复现直接 **Re-run** 换一台 runner |
| 手动跑 `AIR-TCBOOT` 后 ONU 也跟着编译了 | 正常现象：`AIR-ONU` 挂在 TCBOOT 的完成事件上，`TEST` 模式也会触发一次 |
| 想临时加插件 | 用 `PACKAGE` 参数，不必改仓库（改仓库要走提交） |

### 2.7 什么时候该改仓库、什么时候用参数

- **一次性、试验性**：用 `Run workflow` 的 `PACKAGE` / `TEST` 参数，不碰代码。
- **长期生效**（默认插件、驱动、主题、IP）：改 `Config/*.txt` 或工作流 `with:` 段，提交后自动流程就会带上。

### 2.8 公开仓库 / 私有仓库

同一套工作流在两种仓库下都能跑，差别只在 runner 规格和计费：

| 项目 | 公开仓库 | 私有仓库 |
| ---- | -------- | -------- |
| 计费 | 标准 runner **免费且不限量** | 从每月 **$12** 的计算额度里扣（GitHub Free 计划）：标准 Linux 2 核按 $0.006/分钟计，约合 2000 分钟；额度用尽且账户没有付款方式时会被阻断 |
| runner 规格 | 4 核 / 16 GB 内存 / 14 GB SSD | 2 核 / 8 GB 内存 / 14 GB SSD |
| 存储 | Artifact 500 MB、Actions 缓存 10 GB/仓库 | 同上 |
| 一次全量编译 | 约 2~4 小时 | 2 核下明显更慢，有逼近单 job 上限的风险 |

> 以上规格与额度以 GitHub 官方文档为准：[托管 runner 规格](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)、[Actions 限制](https://docs.github.com/en/actions/reference/limits)、[Actions 计费](https://docs.github.com/en/billing/concepts/product-billing/github-actions)。
>
> 磁盘要单独留意：官方表格标的是 14 GB SSD，但实测同一镜像会出现 72 GB 与 145 GB 两种规格（[actions/runner-images#14492](https://github.com/actions/runner-images/issues/14492)），所以工作流不写死盘大小，改成先探测再决定编译盘与 swap。


**不需要为私有仓库改任何配置**，工作流与脚本会自动降级：

- **并行度**：`Scripts/build-core.sh` 的 `auto_jobs()` 取「CPU 核数」与「内存 × 2/3」的较小值，2 核 / 8 GB 会得到 2 路；`rust` host 包还会再单独按内存限到 1~2 路（它是内存大户，8 GB 机器放开必被 OOM 杀掉）。
- **swap**：先探测编译盘余量，再按内存决定建 4~8 GB swap；盘小就少建，余量不足时干脆不建并打 warning。
- **磁盘**：`/mnt` 只有是独立挂载时才拿来做编译盘，否则退回根分区；建 swap 前会先删掉镜像里预装的大目录（.NET / Android SDK / GHC / Boost 等）腾空间。

私有仓库下要留意的两点：

- **单 job 硬上限 6 小时**（`WRT-CORE.yml` 的 `timeout-minutes: 360`，无法再调大）。2 核跑首次全量编译有超时可能，真超了直接 **Re-run**，已有缓存能让它少走一大段。
- 私有仓库的 Release 也是私有的，别人要下载固件得先有仓库权限；要把固件公开给外人的话，还是用公开仓库。

## 第 3 章 改完东西如何生效

| 改动 | 生效方式 |
| ---- | -------- |
| `Config/*.txt`（插件开关、驱动） | 云编译：直接重跑工作流；本地：重跑 `local-build.sh`（复用源码目录即可） |
| `Scripts/Packages.sh`（插件增删/版本） | 同上；本地若插件目录已存在，需要 `--force-clone` 或手动删掉该插件目录后重跑 |
| `Scripts/Settings.sh`（默认主题/IP/WiFi） | 同上 |
| `Scripts/build-core.sh` / `local-build.sh` | 云编译与本地编译同时生效 |
| `.github/workflows/*.yml` | 只影响云编译 |
| `Config/PRIVATE.txt` / `Scripts/PRIVATE.sh` | 私有定制，同样自动拼接/执行（可 `.gitignore` 掉不外发） |
